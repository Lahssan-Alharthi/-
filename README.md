# بوابة الموظفين — شركة مدد للخدمات اللوجستية

بوابة موظفين متكاملة باللغة العربية (RTL) تغطي دورة شؤون الموظفين كاملة إضافةً إلى العمليات
اللوجستية الخاصة بالشركة: الحضور، الإجازات، الرواتب، طلبات الخدمات، المستندات، الأسطول والرحلات،
التقارير، وسجل النشاط.

---

## التشغيل السريع

```bash
npm install          # تثبيت الاعتماديات
npm run seed         # تهيئة قاعدة البيانات ببيانات تجريبية
npm start            # تشغيل الخادم على http://localhost:3000
```

للتطوير مع إعادة التشغيل التلقائي: `npm run dev`
لإعادة بناء قاعدة البيانات من الصفر: `npm run reset`
لتشغيل الاختبارات: `npm test` (93 اختباراً)
لجولة تجريبية كاملة تطبع تقرير النتائج: `npm run demo`

**المتطلبات:** Node.js إصدار 22.5 أو أحدث (يستخدم المشروع وحدة `node:sqlite` المدمجة).

## الربط بالأنظمة الخارجية

واجهة `‎/api/v1` مخصّصة للأنظمة الخارجية: أنظمة المحاسبة، أجهزة البصمة، أنظمة تتبّع المركبات،
وتطبيقات الجوال. توثيقها بمفتاح ربط لا بجلسة مستخدم، ولا تُقبل فيها كوكيز الجلسة.

### إنشاء مفتاح

من **إعدادات النظام ← مفاتيح الربط** (متاح لمدير النظام فقط). يُعرض المفتاح **مرة واحدة عند
إنشائه فقط** — لا يُخزَّن منه في قاعدة البيانات إلا تلبيدة SHA-256، فإن فُقد وجب إنشاء غيره.

```bash
curl -H "Authorization: Bearer mdd_live_xxxxx" https://<host>/api/v1/ping
# أو
curl -H "X-API-Key: mdd_live_xxxxx" https://<host>/api/v1/ping
```

### نطاقات الوصول

المفتاح لا يملك إلا ما يُمنح له صراحةً، فامنح أقل ما يكفي:

| النطاق | يتيح |
|---|---|
| `employees:read` | قراءة بيانات الموظفين **بدون** الرواتب والحسابات البنكية |
| `departments:read` | قراءة الأقسام |
| `attendance:read` | قراءة سجلات الحضور |
| `attendance:write` | دفع سجلات الحضور من أجهزة البصمة |
| `leaves:read` | قراءة طلبات الإجازات |
| `payroll:read` | قراءة الرواتب — وهو ما يفتح الحقول المالية في `employees` أيضاً |
| `fleet:read` / `fleet:write` | قراءة الأسطول / تحديث الحالة والعدّاد |
| `trips:read` / `trips:write` | قراءة الرحلات / إنشاؤها وتحديث حالتها |

### المسارات

| الطريقة | المسار | النطاق |
|---|---|---|
| `GET` | `/api/v1/ping` | أي مفتاح صالح |
| `GET` | `/api/v1/employees` | `employees:read` |
| `GET` | `/api/v1/employees/:employeeNo` | `employees:read` |
| `GET` | `/api/v1/departments` | `departments:read` |
| `GET` | `/api/v1/attendance` | `attendance:read` |
| `POST` | `/api/v1/attendance` | `attendance:write` |
| `GET` | `/api/v1/leaves` | `leaves:read` |
| `GET` | `/api/v1/payroll/runs` | `payroll:read` |
| `GET` | `/api/v1/payroll/runs/:id/payslips` | `payroll:read` |
| `GET` | `/api/v1/fleet` | `fleet:read` |
| `PATCH` | `/api/v1/fleet/:plate` | `fleet:write` |
| `GET` | `/api/v1/trips` · `/api/v1/trips/:code` | `trips:read` |
| `POST` | `/api/v1/trips` | `trips:write` |
| `PATCH` | `/api/v1/trips/:code/status` | `trips:write` |

يُستخدم **الرقم الوظيفي** و**رقم اللوحة** و**رمز الرحلة** كمعرّفات خارجية لأنها ثابتة في أنظمة
الشركة، بدل المعرّفات الداخلية.

### دفع الحضور من جهاز بصمة

```bash
curl -X POST https://<host>/api/v1/attendance \
  -H "Authorization: Bearer mdd_live_xxxxx" \
  -H "Content-Type: application/json" \
  -d '{"records":[
        {"employee_no":"1009","date":"2026-07-20","check_in":"08:40","check_out":"17:20"},
        {"employee_no":"1010","date":"2026-07-20","check_in":"07:58","check_out":"17:05"}
      ]}'
```

يحتمل الطلب حتى 500 سجل، ويُحسب التأخير والوقت الإضافي تلقائياً حسب سياسة الدوام. وإعادة دفع
اليوم نفسه **تحدّث** السجل ولا تكرّره. النتيجة تفصّل كل سجل على حدة فلا تُفشل الدفعة كلها بسبب
سجل واحد: رمز `201` إذا قُبلت جميع السجلات، و`207` إذا قُبل بعضها.

### الترقيم وحد الطلبات

الاستجابات المتعدّدة مرقّمة (`page`، `limit` بحد أقصى 200) وتُعيد كائن `pagination`. ولكل مفتاح
حدّ طلبات في الدقيقة (600 افتراضياً، قابل للضبط)، وتُعاد الترويسات:
`X-RateLimit-Limit`، `X-RateLimit-Remaining`، `X-RateLimit-Reset`، ومع رمز `429` ترويسة `Retry-After`.

كل عمليات الكتابة القادمة من الأنظمة الخارجية تُسجَّل في سجل النشاط باسم المفتاح المستخدم.

## التطبيق على الجوال

البوابة **تطبيق ويب قابل للتثبيت (PWA)** — لا حاجة لمتجر تطبيقات:

- **التثبيت:** يظهر زر التثبيت في الشريط العلوي على المتصفحات الداعمة، أو عبر «إضافة إلى الشاشة
  الرئيسية». وعلى iOS من قائمة المشاركة في Safari.
- **العمل دون اتصال:** يُخزَّن هيكل التطبيق وآخر البيانات المقروءة، فتفتح البوابة وتعرض لوحة
  التحكم وسجل الحضور والإعلانات حتى بلا شبكة، مع شريط سفلي يوضّح أن البيانات محفوظة وليست محدّثة.
- **تسجيل حضور مؤجّل:** إن سجّل الموظف حضوره أو انصرافه وهو بلا تغطية — وهو حال السائقين على
  الطرق — يُحفظ الإجراء محلياً ويُرسل تلقائياً عند عودة الشبكة، مع عدّاد ظاهر للإجراءات المعلّقة.
  عمليات الكتابة لا تُخزَّن في ذاكرة العرض أبداً، فلا تُعرض نتيجة غير حقيقية.
- **اختصارات:** تسجيل الحضور، طلب إجازة، رحلاتي، وإشعارات الراتب — من قائمة أيقونة التطبيق.

الأيقونات مولّدة برمجياً بلا اعتماديات (`npm run icons`) في `public/icons/`، وتشمل نسخة
`maskable` لأندرويد و`apple-touch-icon` لأجهزة iOS.

> يتطلّب تثبيت التطبيق وعمل ذاكرة التخزين تشغيل الموقع على **HTTPS** (أو `localhost` للتطوير).

## البنية التقنية

- **الخادم:** Node.js + Express
- **قاعدة البيانات:** SQLite عبر وحدة `node:sqlite` المدمجة في Node — بلا اعتماديات أصلية
- **الواجهة:** HTML/CSS/JavaScript بلا إطار عمل وبلا خطوة بناء، تطبيق صفحة واحدة بموجّه `hash`
- **الجوال:** تطبيق ويب قابل للتثبيت (PWA) مع عامل خدمة للعمل دون اتصال
- **المصادقة:** JWT في كوكي `HttpOnly` للمستخدمين، ومفاتيح بنطاقات وصول للأنظمة الخارجية
- **التكامل:** سحب عبر `‎/api/v1` ودفع عبر webhooks موقّعة بـ HMAC-SHA256
- **تشفير كلمات المرور:** `scrypt` من `node:crypto` مع مقارنة ثابتة الزمن

## احتساب التأمينات الاجتماعية

الوعاء الخاضع للاشتراك = **الراتب الأساسي + بدل السكن**، بحدّ أقصى شهري قدره 45,000 ر.س.

| الفئة | إجمالي الاشتراك | حصة الموظف (تُخصم من الراتب) | حصة صاحب العمل (تكلفة على الشركة) |
|---|---|---|---|
| سعودي | **22%** | 10% | 12% |
| غير سعودي | **2%** (أخطار مهنية) | لا يوجد | 2% |

**الفارق المهم:** حصة الموظف وحدها هي التي تُخصم من صافي راتبه، أمّا حصة صاحب العمل فتُحتسب
وتُخزَّن وتظهر في المسيّر والتقارير كتكلفة على الشركة، ولا تمسّ راتب الموظف. وفرع الأخطار المهنية
لغير السعوديين يتحمّله صاحب العمل بالكامل، فلا يُخصم من الموظف غير السعودي أي مبلغ.

مثال (سعودي براتب أساسي 9,000 وبدل سكن 2,250):

```
الوعاء              = 11,250 ر.س
إجمالي الاشتراك 22% =  2,475 ر.س
  حصة الموظف   10%  =  1,125 ر.س   ← تُخصم من صافي الراتب
  حصة الشركة   12%  =  1,350 ر.س   ← تكلفة على الشركة
```

### ضبط النسب

كل النسب قابلة للتعديل من `server/config.js` تحت `payroll.gosi` بلا تغيير في الكود:

```js
gosi: {
  saudi:    { totalRate: 0.22, employeeRate: 0.10 },
  nonSaudi: { totalRate: 0.02, employeeRate: 0 },
  maxContributoryWage: 45000,   // 0 = بلا حد أقصى
}
```

> لو أردت خصم كامل الـ 22% من الموظف السعودي بدل 10%، اضبط `employeeRate: 0.22`.

### النسب التدريجية للمشتركين الجدد

النظام يدعم جدولاً تدريجياً للسعوديين الذين بدأ اشتراكهم في التأمينات بعد تاريخ محدّد
(تعديلات 2024)، ويُقرأ تاريخ بدء الاشتراك من حقل `gosi_join_date` في ملف الموظف، أو من
تاريخ التعيين إن لم يُسجَّل:

```js
progressive: {
  enabled: false,                     // معطّل افتراضياً
  newSubscriberFrom: '2024-07-03',
  schedule: {
    2026: { totalRate: 0.21, employeeRate: 0.095 },
    2027: { totalRate: 0.22, employeeRate: 0.10 },
    // ...
  },
}
```

> **معطّل افتراضياً**، والأرقام في الجدول قيم مبدئية قابلة للضبط. فعّله فقط بعد مطابقة
> الجدول الرسمي الصادر من المؤسسة العامة للتأمينات الاجتماعية.

وتُخزَّن الشريحة المطبّقة مع كل إشعار راتب في حقل `gosi_tier` (`base` أو `progressive:YYYY`
أو `occupational_hazards`) لتكون المراجعة ممكنة لاحقاً.

### تحديد الفئة

تُشتَقّ الفئة من حقل **الجنسية** في ملف الموظف، مع تحمّل اختلاف الصياغة
(`سعودي`، `سعودية`، `السعودية`، `Saudi`، `KSA`). الموظف الذي لا جنسية مسجّلة في ملفه يُحتسب
كغير سعودي، ويظهر تنبيه صريح بأسماء هؤلاء عند توليد المسيّر لتصحيح ملفاتهم.
وتظهر فئة كل موظف في إشعار الراتب وفي جدول المسيّر لتكون قابلة للمراجعة.

## السلف والتقسيط المرن

السلفة لا تُخصم مرة واحدة، بل على أقساط شهرية **يحدّدها صاحب الصلاحية** (الشؤون المالية أو
مدير النظام) بإحدى طريقتين، ويُشتقّ الآخر تلقائياً:

| الطريقة | المُدخل | النتيجة |
|---|---|---|
| بعدد الأقساط | 12 قسطاً على 12,000 | 1,000 ر.س شهرياً |
| بمبلغ القسط | 750 ر.س شهرياً على 9,000 | 12 قسطاً |

ويُحسب الجدول أمام المستخدم أثناء الإدخال، فيرى النتيجة قبل الحفظ.

### سلوك الخصم

- **القسط الأخير يستوعب كسر التقريب**: 2,500 على 3 أقساط = 833.33 + 833.33 + **833.34**،
  فيُسدَّد المبلغ كاملاً بعدد الأقساط المحدّد بلا قسط إضافي بقيمة قروش.
- **لا يُسجَّل القسط مسدّداً إلا عند اعتماد المسيّر** — مسيّر مسودة أو محذوف لا يمسّ الرصيد.
- **لا يُخصم الشهر مرتين** ولو أُعيد توليد المسيّر.
- **إعادة الجدولة** تُطبَّق على المتبقّي فقط ولا تمسّ الأقساط المسدّدة.
- **الإيقاف** يوقف الخصم ويبقي المتبقّي غير مخصوم (لتسوية نقدية أو إعفاء).
- تُقفل السلفة تلقائياً عند سداد كامل المبلغ.

الحد الأقصى لعدد الأقساط قابل للضبط من `config.payroll.maxLoanInstallments` (24 افتراضياً).

## مخالصة نهاية الخدمة

### مكافأة نهاية الخدمة

على أساس نظام العمل السعودي (المادتان 84 و85):

| مدة الخدمة | الاستحقاق |
|---|---|
| السنوات الخمس الأولى | نصف أجر شهر لكل سنة |
| ما بعد الخمس سنوات | أجر شهر كامل لكل سنة |

وكسور السنة تُحسب بنسبتها. وفي حالة **الاستقالة** تُطبَّق نسبة على المكافأة:

| مدة الخدمة | نسبة الاستحقاق |
|---|---|
| أقل من سنتين | لا شيء |
| من سنتين إلى أقل من خمس | الثلث |
| من خمس إلى أقل من عشر | الثلثان |
| عشر سنوات أو أكثر | كامل المكافأة |

### مكوّنات المخالصة

```
  مكافأة نهاية الخدمة
+ بدل الإجازات غير المستنفدة
+ مستحقات أخرى
− أرصدة السلف القائمة
− استقطاعات أخرى
─────────────────────
= صافي المخالصة
```

**بدل الإجازات يُحتسب بالتناسب** مع مدة العمل خلال السنة: من عمل تسعة أشهر يستحق نحو
22.5 يوم من رصيد 30، لا الرصيد كاملاً — مطروحاً منه ما استُهلك.

### دورة العمل

1. **تقدير** فوري بلا حفظ للاطلاع قبل القرار (`/api/end-of-service/estimate/:employeeId`).
2. **مسودة** تُعدّها الموارد البشرية، ولا يراها الموظف.
3. **اعتماد** من المالية أو مدير النظام: يُنهي خدمة الموظف، ويسوّي سلفه القائمة لأنها
   حُسمت في المخالصة، ويُشعر الموظف، ويبثّ حدث `end_of_service.approved`.
4. **تعليم كمصروفة** بعد الصرف الفعلي.

ولا يمكن إعداد مخالصة ثانية لموظف قبل صرف الأولى، ولا اعتماد المخالصة مرتين.

> **معدّلات المكافأة والنسب قابلة للضبط** من `config.payroll.endOfService`. راجعها مع
> المختص القانوني قبل الاعتماد عليها في مخالصة فعلية، وتحقّق ممّا يدخل في «الأجر» لدى شركتكم
> (`includeAllowances` يضمّ البدلات الثابتة افتراضياً).

## دفع الأحداث (Webhooks)

بدل أن تستعلم الأنظمة الخارجية البوابة باستمرار، تدفع البوابة الأحداث إليها لحظة وقوعها.
تُدار الاشتراكات من **إعدادات النظام ← دفع الأحداث** (لمدير النظام).

### الأحداث المتاحة

`employee.created` · `employee.terminated` · `attendance.recorded` · `leave.requested` ·
`leave.decided` · `request.decided` · `payroll.approved` · `trip.created` ·
`trip.status_changed` · `vehicle.maintenance` · `loan.created` · `end_of_service.approved`

### شكل الطلب

```http
POST /your/endpoint
X-Madad-Event: leave.decided
X-Madad-Timestamp: 1793491200
X-Madad-Signature: sha256=<التوقيع>
X-Madad-Attempt: 1

{
  "event": "leave.decided",
  "sent_at": "2026-11-01T09:00:00.000Z",
  "company": "شركة مدد للخدمات اللوجستية",
  "data": {
    "employee_no": "1009",
    "leave_type": "ANNUAL",
    "start_date": "2026-11-07",
    "end_date": "2026-11-10",
    "days": 4,
    "decision": "approved"
  }
}
```

### التحقّق من التوقيع

يُحسب التوقيع على `"الطابع الزمني" + "." + "نص الطلب"` بمفتاح السر الذي يُعرض مرة واحدة
عند إنشاء الاشتراك:

```js
const expected = crypto.createHmac('sha256', secret)
  .update(`${req.headers['x-madad-timestamp']}.${rawBody}`)
  .digest('hex');

if (`sha256=${expected}` !== req.headers['x-madad-signature']) return res.sendStatus(401);
```

**تحقّق من التوقيع دائماً**، ومن ألا يتجاوز عمر الطابع الزمني بضع دقائق، قبل الاعتماد على
محتوى الحدث.

### سلوك التسليم

- **إعادة المحاولة:** حتى 4 محاولات بتباعد 0 ثم 5 ثوانٍ ثم 30 ثم 120، ومهلة كل محاولة 10 ثوانٍ.
- **أخطاء `4xx`** لا تُعاد المحاولة فيها (عدا `429`) لأن الخطأ في الطلب لا في الشبكة.
- **الإيقاف التلقائي:** بعد 10 أعطال متتالية يُوقف الاشتراك ويُسجَّل السبب، وإعادة تنشيطه
  تصفّر العدّاد.
- **سجل التسليم:** كل محاولة مسجّلة برمز الاستجابة ومدّتها وسبب الفشل، ويمكن استعراضها من
  شاشة الإدارة أو إرسال حدث تجريبي للتحقّق من الربط.
- **فشل الحدث لا يُفشل العملية الأصلية** — الإرسال يجري في الخلفية بعد نجاح العملية.
- **حماية من SSRF:** في بيئة الإنتاج يُلزم HTTPS وتُرفض عناوين الشبكة الداخلية.

## نموذج الصلاحيات

الصلاحيات معرّفة في `server/utils/rbac.js` بصيغة `المورد:الإجراء`، وتُفرَض على الخادم في كل مسار —
إخفاء عنصر في الواجهة ليس اعتماداً على الأمان. أبرز القواعد المطبّقة:

- الموظف يرى سجل حضوره ورحلاته وإشعارات راتبه فقط.
- المدير المباشر يعتمد إجازات فريقه فقط، ولا يعتمد إجازته الشخصية.
- بيانات الرواتب والحسابات البنكية محجوبة عمّن لا يملك `payroll` أو صلاحية الموارد البشرية.
- الموظف يعدّل حقولاً شخصية محددة فقط؛ أي محاولة لتعديل الراتب أو الدور تُتجاهَل على الخادم.
- إشعارات الرواتب لا تظهر للموظفين قبل اعتماد المسيّر.
- كل إجراء مؤثّر يُسجَّل في `audit_logs` مع المستخدم وعنوان الـ IP.

إضافات أمنية أخرى: تحديد محاولات الدخول الفاشلة، فحص أنواع الملفات المرفوعة وحجمها، ترويسات
`CSP` و`X-Frame-Options` و`nosniff`، واستعلامات مُعامَلة بالكامل ضد حقن SQL.

**مفاتيح الربط:** لا يُخزَّن المفتاح بل تلبيدته فقط، ولا يُعرض إلا مرة واحدة عند إنشائه. ولكل
مفتاح نطاقات محدّدة وحدّ طلبات وتاريخ انتهاء اختياري. والإلغاء لا يحذف السجل حتى يبقى أثره في
المراجعة. وواجهة الربط لا تقبل جلسات المستخدمين، كما أن الجلسة لا تُقبل بديلاً عن المفتاح.

## ملاحظات قبل التشغيل في بيئة إنتاج

1. اضبط `JWT_SECRET` بقيمة عشوائية طويلة، وشغّل خلف HTTPS (الكوكي يصبح `secure` تلقائياً عند
   `NODE_ENV=production`).
2. البيانات التجريبية مخصّصة للعرض — استخدم `npm run reset` ثم أنشئ الحسابات الحقيقية، وغيّر
   كلمات المرور الافتراضية.
3. مجلد `data/` (قاعدة البيانات والمرفقات) خارج نطاق Git ويحتاج نسخاً احتياطياً منتظماً.
4. نسب التأمينات الاجتماعية وطريقة خصم الغياب والسلف مبنية على إعدادات قابلة للتعديل في
   `server/config.js` — راجع [قسم احتساب التأمينات](#احتساب-التأمينات-الاجتماعية) وتأكّد من
   موافقتها لسياسة الشركة ولوائح المؤسسة العامة للتأمينات الاجتماعية قبل الصرف الفعلي. النسب
   التدريجية للمشتركين الجدد مدعومة لكنها **معطّلة افتراضياً** حتى تُطابق الجدول الرسمي.
